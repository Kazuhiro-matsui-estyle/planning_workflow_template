# 機能追加の計画ワークフロー（汎用テンプレート）

既存のコードベースに機能を足すとき、**実装の前に「何をどこまで変えるのか」を
複数のサブエージェントで調べて計画する**ための仕組みです。

単一のエージェントに計画させるより深く、見落としが少なくなります。
特徴は3つです。

- **関心軸ごとに並列調査する** — ディレクトリで割らないので、設定・テレメトリ・
  マイグレーションのような横断的な仕組みが「誰の担当でもない」状態にならない
- **影響範囲の主張を反証しにいく** — 「Xを変えると影響するのはA,B,Cだけ」という主張を、
  別のエージェントが grep で崩しにかかる
- **決めるべきことを人に返す** — エージェントが勝手に決めず、選択肢と推奨と決定期限を出す

導入手順は **[SETUP.md](SETUP.md)** を参照してください。

> コマンド名は `/plan-survey` と `/plan-feature` です。
> よくある `feature-plan` という名前を避けているのは、既存のスキルと衝突しないようにするためです。

---

## 全体の流れ

```
 ① /plan-survey を1回              約10〜20分
      ↓
   docs/plan/repo-baseline.md         コードの地図
   docs/plan/regression-checklist.md  回帰確認の手順書
   docs/plan/feature-order.md         依存関係・着手順・確認すべきこと
      ↓
 ② blocking_questions に答える      人間が判断
      ↓
 ③ /plan-feature <機能キー>         機能ごとに1回
      ↓
   docs/plan/<機能キー>.md            実装計画（検証手順を含む）
      ↓
 ④ open_decisions に答える → refine: true で再実行
      ↓
 ⑤ 実装させる                      ★step ごとに 4〜9章を横断で読ませる
      ↓
 ⑥ 回帰チェックリストを一通り実行   ★機能を1つ実装するたびに必ず
      ↓
 ⑦ 次のセッション開始時、フックが git 差分を見て知らせる
      ↓
   project-rules.md に追記（あなたが書く。Claude が文面案を出す）
      ↓
   次の機能へ（③に戻る）
```

**②と④の「人間が答える」を飛ばさないでください。**
ワークフローは実行中に質問できません。質問は出力として返るので、
それに答えてから次に進む設計です。

## ファイルの役割

### あなたが書くもの（手書き）

| ファイル | 役割 | いつ更新するか |
|---|---|---|
| `.claude/workflows/project-rules.md` | 確定した前提と地雷。**全エージェントが最初に読む** | 実装や調査で新しい事実が分かったとき |
| `.claude/workflows/backlog.md` | 機能の一覧と仕様。機能キーもここ | 仕様が固まったとき |
| `CLAUDE.md` | 新しいセッション・ブランチへの申し送り。要点だけを書き、手順の本体は下の2つに分けている | 導入時に1回 |
| `.claude/workflows/fix-procedure.md` | 指摘・症状を直す手順（仕分け → 原因の確定 → 計画書 → 再現テストと守りのテスト → 直す → 出力の突き合わせ）。CLAUDE.md が「直す前に必ず開く」と指示する | 運用を変えるとき |
| `.claude/workflows/verification.md` | 検証の手順（層の表・手動確認・実体の突き合わせ・E2E）。CLAUDE.md「### 6.」(1)〜(5) の本体 | 導入時に「（このプロジェクトの…）」を埋める |

> **`docs/plan/<機能キー>-note.md` は手書きです。**
> 決めた仕様・設計判断・open_decisions の回答を書き溜める場所で、
> **計画書はここから要約を作ります。** ワークフローはこのファイルを自分では読まないので、`/plan-feature` を回すときに本文を `note:` に渡してください（下の③）。要約に落ちる過程で
> 「なぜその案を捨てたか」が削られるので、実装時は note 側の本文も開かせること。

### ワークフローが生成するもの

| ファイル | 役割 | 生成元 |
|---|---|---|
| `docs/plan/repo-baseline.md` | コードの地図 | `/plan-survey` |
| `docs/plan/regression-checklist.md` | 回帰確認の手動QA手順書 | `/plan-survey`（全体実行時のみ） |
| `docs/plan/feature-order.md` | 機能間の依存と着手順 | `/plan-survey`（全体実行時のみ） |
| `docs/plan/<機能キー>.md` | 機能ごとの実装計画 | `/plan-feature` |
| `docs/plan/.baseline-commit` | 鮮度チェック用の基準コミット | `/plan-survey` |

### 仕組み側（普段触らない）

| ファイル | 役割 |
|---|---|
| `.claude/workflows/plan-survey.js` | リポジトリ調査（10エージェント / 部分調査は3〜5） |
| `.claude/workflows/plan-feature.js` | 機能1つの計画（12エージェント / refine は8） |
| `.claude/hooks/check_plan_freshness.py` | セッション開始時に project-rules への追記を促す |

> **注意: `project-rules.md` を更新しても `repo-baseline.md` は変わりません。**
> 別系統です。project-rules は「何に気をつけるか」の知見、baseline は「どこに何があるか」の地図。
> 地図の更新は `/plan-survey` を回したときだけ起きます。

## ① リポジトリを調査する（1回だけ）

```
/plan-survey
```

**7つのレンズ**が並列で走ります（`ui` を外せば6つ）。

| レンズ | 何を調べるか |
|---|---|
| `precedent` | 機能ごとに最も近い既存実装と、それが触る全ファイル ← **最重要** |
| `state` | データと設定の住処 |
| `wiring` | 新しい単位の登録経路（登録漏れで動かない箇所） |
| `contracts` | 層をまたぐ契約（文字列一致・型・スキーマ） |
| `crosscut` | エラー・認可・ログ・バリデーション・非同期 |
| `ui` | 画面の構造 |
| `verify-deploy` | 検証手段と出荷手順 |

**引数（すべて任意）**

```js
{
  lenses: ['ui', 'contracts'],       // 指定したレンズだけ再調査（部分調査）
  done: ['feature-a', 'feature-b'],  // 実装済み。着手順から除外される
  extraLenses: ['プロジェクト固有の関心軸を自由記述'],   // 最大4本
  readonlyAgentType: 'Plan',         // 既定。読み取り専用で深く読む
  allowWrite: false,                 // 既定。true にすると調査側も書き込み可（非推奨）
}
```

### 部分調査

```
/plan-survey  lenses: ['ui', 'contracts']
```

`repo-baseline.md` の**指定レンズの記述だけ差し替える**（他はそのまま残る）。
`regression-checklist.md` と `feature-order.md` は更新しません。3〜5エージェント。

## ③ 機能ごとに計画する

```
/plan-feature search-filter
```

**機能の数だけ実行します。** 自動で全機能は走りません。

```js
{
  feature: 'search-filter',        // 必須。backlog.md の機能キー
  note: '決まった仕様をここに', // ②で決めたこと、合意したこと
  refine: false,              // true にすると「計画の更新」モード（④）
  maxRefute: 3,               // 反証する影響範囲の主張の数
  maxRefill: 2,               // 批評で見つかった穴を再調査する数
  extraProbes: ['この機能特有の調べてほしいこと'],  // 最大2本
}
```

**`note` が精度を大きく変えます。** 空だと「決めるべきこと」として `open_decisions` に出ます。

各エージェントは実行時に `backlog.md` / `project-rules.md` /
`repo-baseline.md` / `feature-order.md` の4つを読みます。

### 5つのフェーズ

| フェーズ | 数 | やること |
|---|---|---|
| Probe | 4 | 前例 / 影響層 / 契約 / 制約 を並列に深掘り |
| Draft | 1 | 設計案・変更計画・影響範囲・決めるべきこと |
| Refute | 3 | 影響範囲の主張を**反証しにいく**（grep で見落としを探す） |
| Gaps | 1+2 | 「何が抜けているか」を批評し、指摘された穴を再調査 |
| Plan | 1 | 最終計画を `docs/plan/<機能キー>.md` に書き出す |

### 出力される計画書

```
 1. 作るものと、見積もりに収まるかの判定
 2. 先に決めてほしいこと（選択肢・推奨・決定期限つき）
 3. 設計案（複数ある場合は比較）
 4. 変更するファイル一覧（真似する既存実装の file:line つき）
 5. 影響範囲（反証を通ったもの / 反証で広がったもの）
 6. 検証手順
 7. 出荷時にやること（project-rules の「出荷の制約」を1項目ずつ判定した結果）
 8. 回帰チェックリストへの追記項目
 9. リスクと未確定事項
10. 実装の順序（各ステップでアプリが壊れないこと）
```

---

## ④ open_decisions に答えて計画を更新する

```
/plan-feature search-filter  refine: true  note: (答え)
```

| | 通常 | refine |
|---|---|---|
| 深掘り調査（Probe 4本） | 実行 | **スキップ** |
| 土台 | コードを1から調査 | **既存の計画書** + 新しい note |
| エージェント数 | 12 | **8** |

深掘りは「コードが今どうなっているか」を調べるもので、人間の決定とは無関係だからです。
Refute と Gaps は残します（決定が変われば影響範囲も変わるため）。

決定を重ねるたびに `open_decisions` が減り、新たな判断事項が出てきます。
ゼロになったら実装に着手できます。

**コードが変わったときは `refine` を使わないでください。** 調査からやり直します。

## ⑤ 実装させる — 計画書10章の順序を守らせる

計画書ができても、**実装させ方で結果が変わります。** ここが一番効きます。

### ステップごとに 4〜9章を横断で読ませる

**10章の表だけを見て実装させないこと。**

計画書は4章（変更するファイル）から9章（リスク）まで、
**同じ変更を別の角度から**書いています。実装者が4章だけを見ると、
そのステップに効く5章の反証・6章のテスト・8章の回帰項目・9章のリスクを落とします。

**落としても実装は動いてしまうので、落としたことに気づけません。**

| 場面 | 指示の例 |
|---|---|
| ステップ着手前 | `step 5 に入る前に、10章のその行の「着手前に読む」を全部開いて、何が書いてあったか要約してから実装して` |
| 読んだか怪しいとき | `step 5 の「踏みうる地雷」を1件ずつ挙げて、それぞれどう対処したか報告して` |
| 章をまたいで拾わせる | `step 5 に着手する前に、5〜9章からこのステップに効く記述を横断で拾って列挙して。該当が無い章はその旨を書いて` |
| 波及先を拾わせる | `step 5 で編集しないのに影響を受けるファイル・画面・API を、5章の blast_radius から挙げて。それぞれ何が起きるかも書いて` |
| 実装後 | `step 5 で新しく分かった事実のうち、project-rules に無いものを追記の文面案として出して` |

**「読んで」ではなく「読んで要約して」「列挙して」と言うこと。**
読んだかどうかは外から見えませんが、要約は見えます。

### 実装させるときに効いた12項目

どれも「**落としても実装は動いてしまう**」種類の失敗を防ぎます。

#### 1. テストを先に書かせ、**赤を確かめさせる**（先に確かめられなかったテストは、直した箇所を一度戻して落ちることを確認させる）

後から書いたテストは**新しい挙動を写し取るだけ**で、壊したかどうかを判定できません。

そして**それ以上に重要なのが反証**です。

```
テストを書いた → 緑になった → 直したところを一時的に元へ戻す → **赤くなるか**
```

**落ちない再現は再現ではありません。**

実際に、反証をしたことで「テストが実装を守れていない」と判明した例:

| | |
|---|---|
| 定数を戻したら**単体テストは全部緑のまま** | 単体は定数しか見ておらず、**経路の途中で切られる事故**を見ていなかった |
| 計測を追加したがスパンを閉じた後に属性を足していた | ライブラリは終了後の書き込みを**例外も出さず無視**する。**テストは緑だった**（スパイが閉じた後の書き込みも記録していたため） |

```
このテストが実装を守れているか確かめたい。直した箇所を一時的に元へ戻して、
テストが落ちることを確認してから復元して。
```

#### 2. **テストダブルは本物のシグネチャから必ず遅れる**

本物の関数に引数を1つ足すと、差し替えているダブルが `TypeError` になります。
**問題はそこではなく、失敗メッセージが原因を指さないこと**です。

```
本物に引数を足した
  → ダブルが受け取れず TypeError
  → 上位の except がそれをエラー応答に変換
  → テストの失敗は「出力の並びが変わった」
  → **「引数が合っていない」とはどこにも出ない**
```

**戻り値の形を変えたときも同型**です。差し替え箇所が10か所あれば10か所すべてが
同じ形で埋もれます。既定の戻り値は変えず、**新しい形はフラグで選ぶ**のが安全です。

対策: **「ダブルが `**kwargs` を受けること」を契約テストで強制する。**

#### 3. **観測できないものは較正できない。閾値を入れるなら、同じ回に記録も入れる**

閾値（上限・回数・しきい値）を決めるには**「発動しなかった回」の分布**が要ります。
発動した回にしか記録していないと、**高すぎるのか低すぎるのかが原理的に測れません。**

そして **運用した日数ぶんのデータは後から復元できません。**

★ **計測のための行が本番の処理を止めないこと。** 独立した `try` で囲みます。

#### 4. **step が「先へ送ったもの」が、送り先の step 行に書いてあるか確認させる**

「これは step N でやる」と判断したものは、**その step の行に書かないと届きません。**
別ファイルや会話に書いても、step 行を読む人の視野には入りません。

**落としても実装は動き、テストも落ちません。** 計画書を読み直す以外に気づく手段がありません。

```
この step が「次の step でやる」と判断したものを列挙して、
10章のその step 行に書いてあるか確認して。無ければその場で追記して。
決定を変えたなら、その決定を参照している step 行を grep して全部直して。
```

#### 5. **顧客に渡す枝は「開発枝から切って、開発用のものを削除する」**

テスト・計画ドキュメント・エージェント用の設定を出さない場合、**削除だけでは足りません。**

| 落とし穴 | |
|---|---|
| **フックの登録が残る** | フック本体を消しても設定ファイルの登録が残り、**存在しないスクリプトを呼ぶ設定**になる |
| **ロックファイルの `name`** | ディレクトリ名が書き込まれる事故（パッケージマネージャをリポジトリルートで実行した副作用） |
| ★ **`.gitignore` を戻すと機密が露出する** | 評価スクリプトの出力（**顧客の実データを含む**）を無視していた行が消え、**`git add -A` 一発で公開リポジトリに載る** |
| **ビルド成果物が2世代同居する** | `git checkout <枝> -- <dir>` は**枝に無いファイルを消さない。** 参照先は新しいほうなので**画面は正常に動き、気づけない** |

**「開発用だから全部戻す」という機械的な判断が危険**なのは3つ目です。

#### 6. **計画書の step に無い修正も、テストより先に計画書を作らせる**

レビュー指摘の修正・頼まれた修正・見つけたバグは、計画書の step に書かれていません。
そのまま直させると、**テストは「指摘された症状」だけを確かめ、直し方が生む新しい組み合わせを見ません。**

実際に起きた例: 「一覧の行を、処理の受付ではなく完了の通知で外す」という修正は、
行が外れるタイミングを非同期に変えるものでした。テストは「全件が消える」だけを見ていて、
**行番号で持っていた選択がずれる・通知が応答より先に届く**、という新しいバグを見逃しました。

計画書（5章の影響範囲・6章のテスト・9章のリスク）を先に書かせると、
「直し方を変えると何が壊れるか」を、テストを書く前に考えさせられます。

```
この修正は計画書の step に無いので、fix-procedure.md の手順で進めて。
先に原因が確定しているか再現して判定し、確定したら docs/plan/<機能キー>-<日付>-<主題>.md を
元の計画書と同じ章立てで作って見せて。承認したら6章のテストから書いて。
```

#### 7. **step ごとにレビューを依頼させる。仕様書は計画書から切り出して渡す**

テストが全部緑になったら、step の変更をローカルでコミットさせ、
固定点（step に着手する直前のコミット）と仕様書を渡してレビューを依頼させます。

**計画書を丸ごと仕様書として渡すと、誤検知が混ざります。** 仕様と照らすレビューは、
渡された文書の全体を「この差分の要件」として読みます。レビューする差分は1 step 分なので、
**まだ手を付けていない後の step が全部「未実装」として指摘されます。**

| この step が | 渡すもの |
|---|---|
| 計画の1つの step | 10章の対象の step と、4・5・6・8・9章の該当範囲を切り出した文書 |
| すべての step にまたがる | 計画書そのもの |

コミットしてから依頼するのは、レビューが `git diff <固定点>...HEAD` を見るためです。
未コミットの変更はレビューされません。

#### 8. **PR に push する前に、その PR の差分だけに code-review を回させる**

レビュー指摘を直すために足したコードは、最初のレビューの後に生まれたものです。
**最初のレビューでは見つけようがありません。**

実際に、指摘を直した PR をレビューせずに push し、直すために足したコードに7件のバグが残りました
（同時実行の判定のすり抜け、選択のずれ、通知の競合など）。
PR の差分（数ファイル・数十行）だけに code-review を回し直したら、すぐに見つかりました。
機能全体のような大きな差分を対象にすると、こうした小さな競合は埋もれます。

```
push する前に、origin/<向け先>...HEAD に code-review を effort high で回して。
実在する指摘を直してテストを流し直し、指摘が0件になってから push して。
```

#### 9. **指摘を直す前に、変わってはいけない振る舞いのテスト（守りのテスト）を足させる**

「赤を確かめてから直す」だけでは、**直す対象の振る舞い**しか守れません。
直したことで周りの振る舞いが変わっても、そこにテストが無ければ、テストを全部流し直しても緑のままです。

実際に、HTML の本文抽出で「フォームの中の選択肢を捨てる」修正をしたとき、
フォームの外の選択肢まで消えるようになっていました。そこを確かめるテストが無かったため、
全テストは緑のままで、レビューで初めて見つかりました。
同じ回に、直す前のコードでも空文字どうしの比較で緑になる（何も確かめていない）テストも見つかっています。

守りのテストは直す前も後も緑なので、「赤を確かめる」の対象になりません。代わりに次の2つを確かめさせます。

- 直す前のコード（固定点）で緑になる
- 守っている振る舞いを一時的に壊すと赤になる（壊しても緑なら、そのテストは何も守っていない）

計画どおりの普通の step でも、5章の後方互換に挙がったものが6章に無ければ、守りのテストとして足させます。

5章で予想していなかった場所の変化は、守りのテストでは拾えません。上の例（フォームの外の選択肢）がそれで、
直したあとに固定点と HEAD に同じ入力を通して出力を突き合わせる方法で見つかりました。
そこで、この突き合わせも手順に入れています。外へ書き込まない、同じ入力で同じ出力になるコードに限ります
（書き込む経路で試すと、共有環境が変わります）。

```
指摘を直す前に、直す箇所の周りで変わってはいけない振る舞いのテスト（守りのテスト）を足して。
計画書5章から守るものを拾って6章に「守りのテスト」として書き、直す前のコードで緑、
守っている振る舞いを一時的に壊すと赤になることを確かめてから直して。
直したあと、固定点と HEAD に同じ入力を通して出力を突き合わせ、意図しない差が無いか見て。
```

#### 10. **直す前に原因を確定させる。曖昧なら `/diagnose` に回させる**

「赤を確かめてから直す」は、原因が分かっていることが前提です。原因が曖昧なまま計画書を書くと、
4章（変更ファイル）が推測で埋まり、承認もその推測に対して出ます。
再現テストが赤にならなかったときの行き先も、決まっていませんでした。

そこで、計画書を書く前に、原因が確定しているかを**観察で**判定させます。
手順の本体は `fix-procedure.md` にあり、CLAUDE.md は「直す前に必ず開く」とだけ指示します。

```
入口: レビューの指摘 → 仕分け（実在しないものは、入口ごとの行き先へ）
      症状・頼まれた修正・見つけたバグ
  ↓
再現を試す（scratchpad）
  ├ 1回目で指摘どおりに赤、誤りの行を file:line で言える → 原因が確定
  └ それ以外 → /diagnose（Phase 5 に入らない）→ 原因と最小の再現を持って計画書へ
  ↓
計画書 → 承認 → 再現テスト（赤）と守りのテスト → 直す → 出力の突き合わせ → CLAUDE.md「### 6.」へ
```

| | |
|---|---|
| 原因が確定 | 再現が1回目で指摘どおりに赤になり、誤りを出す行を `file:line` で言える |
| `/diagnose` の止めどころ | Phase 1〜4（ループ作り・再現と最小化・仮説・計装）で原因を突き止めたら止める。Phase 5（修正）に進むと、計画書の承認・守りのテスト・出力の突き合わせを飛ばしてしまう |
| diagnose のループ | 外へ書き込まない経路に限る。書き込みが絡む症状は、ユーザーが実行する手順を出す |

`/diagnose` は Claude からは起動できない設定（`disable-model-invocation: true`）なので、
review-full と同じく、コマンドを提示して止まります。

```
この指摘は再現テストが赤にならなかったので、/diagnose に回すコマンドを出して止まって。
diagnose は Phase 5（修正）に入らずに止めて、原因と最小の再現を持って計画書から始めて。
```

#### 11. **自動化できるものは E2E に回させる。E2E には事故止めを入れる**

手動の検証は、実際にデータが変わるものだけに絞ります。それ以外で単体テストでも結合テストでも確かめられないもの
（フロント・バック・外部サービスが実際につながっているか）は、手動に流さず E2E に回させます。
どの層で確かめるかは、テンプレートの `verification.md` の「(5)」の表で決めさせます。

E2E を作るときに入れておくと効いたものは次のとおりです。

| 入れるもの | 防いだこと |
|---|---|
| 配信中のビルド成果物とリポジトリの成果物を突き合わせ、食い違えば1本も走らせない | ビルドのし忘れで古いコードを検証していた。別のディレクトリのサーバがポートを掴んでいて、別のコードを検証していた |
| 書き込みを実行時に遮断する（grep ではなく、リクエストの横取りで） | E2E ではどの API が飛ぶかをアプリのコードが決めるので、テストのソースを見ても書き込みに気づけない |
| 遮断を組み込んだ `test` からの import を、契約テストで強制する | 素の `test` を使った spec が、遮断の効かないまま共有環境を壊す |
| 検索や生成を伴う確認は、既存の spec の末尾に足す | 1回ごとに LLM の費用とログの書き込みが増える |
| アプリを起動するスクリプトを決める | 環境変数が入らずに落ちたのを、ネットワークの問題と読み違える |

#### 12. **約束ごとに確かめ方を書かせ、実装の前に反例を探させる**

計画書の5章に「変わってはいけない振る舞い」を書いても、それだけでは守れません。
**確かめる道具が、その約束に効く入力を見ていなければ、後退はレビューまで見つかりません。**
また、計画書と実装は「こう変わるはず」を確かめる向きで作るので、壊れる入力を探す向きの検査は、
実装の後のレビューで初めて入ります。そのたびに、計画書から1往復かかります。

実際に、パーサの修正で修正とレビューを4往復したことがあります。5章には「ある要素の外の出力は変えない」と
書いてあったのに、確かめるスクリプトはその要素を含まない入力しか見ておらず、後退をレビューで初めて知りました。
正解の基準（仕様どおりの参照実装）と過去の版を使って、ランダムな入力で後退を数えるようにしてからは、
後退を0件にしてからレビューに出せるようになりました。

そこで、次の2つを手順に入れています（CLAUDE.md「### 4.」と `fix-procedure.md` の手順3）。

| | |
|---|---|
| 約束ごとの確かめ方 | 5章の「変わってはいけない振る舞い」の1行ごとに、どの道具が・どの入力の集合で確かめるかを書く。入力の集合が約束を覆っているか（約束に効く組み合わせ・位置・状態が入っているか）を見る。確かめ方の無い行は、6章か10章に足してから着手する |
| 実装の前の反例探し | 多くの入力や呼び出し元に効く規則・共通の関数を変えるときは、試作して、壊す入力を探す向きのサブエージェントを1本走らせる。正解の基準（仕様・参照実装・前の版の出力）と過去の版を道具として渡す。見つかった反例は計画書に足してから本実装に入る |

```
この修正は共有の規則を変えるので、計画書を書く前に scratchpad で試作して、
壊す入力を探すエージェントを1本走らせて。5章の約束ごとに、どの道具がどの入力で確かめるかも書いて。
```

## ⑥ 実装したら回帰チェックリストを一通り実行する

**機能を1つ実装するたびに、必ず `docs/plan/regression-checklist.md` を上から順に確認してください。**

各機能の計画書の**8章**に、その機能で増える確認項目が**そのまま貼れる形**で出ます。

```
- [ ] 一覧画面で 👍 を押す → ボタンが押下状態になる        (new-flow)
- [ ] ログをCSV出力 → 評価列が入っている                  (changed-existing) [外部接続]
```

`changed-existing` は「既存の項目を書き換える」合図です。
**チェックリストは実装のたびに長くなります。それが正しい状態です。**

## ⑦ フックが追記を促す

`.claude/hooks/check_plan_freshness.py` が SessionStart で動き、
「`project-rules.md` を最後に更新した時点」より後に変わったソースを git 差分から拾います。

判定はコミット SHA が基準なので、**新しいセッションでも新しいブランチでも効きます。**

| 度合い | 判定条件 | 知らせる内容 |
|---|---|---|
| 軽微 | 影響レンズ 1個 | 「project-rules への追記を」だけ |
| 中程度 | 影響レンズ 2〜4個 | 追記 +「部分調査もできます」 |
| **大規模** | **ディレクトリ新設・移動・削除**<br>または レンズ5個以上 / 30ファイル以上 | 追記 +「**★全体再作成を推奨**」 |

### なぜ「形の変更」だけ特別扱いなのか

`repo-baseline.md` の `precedent`（機能 → 真似すべき既存実装のパス対応表）が
**丸ごとずれる**からです。`precedent` は全機能に効くので、以降の全計画の精度が落ちます。

中身が変わっただけなら部分調査で足ります。**パスが動いたときだけ全体を回す**、が判断基準です。

**通知するだけで、実行はしません。** Claude が確認してから回します。

## 書き込みについて

**ソースコードには一切触れません。**

- 調査・草案・反証・批評のエージェントは**読み取り専用**（`Plan` エージェント。Edit / Write を持たない）
- ファイルを書くのは最終フェーズだけで、書き先は `docs/plan/` 配下のみ

`allowWrite: true` でこの制限を外せますが、通常は使いません。

## メンテナンス

**JS は普段触りません。** 更新するのは手書きの `.md` 2つだけです。

| ファイル | いつ |
|---|---|

| `backlog.md` | 仕様が固まったとき |

計画の質が落ちてきたと感じたら、まずこの2ファイルの鮮度を疑ってください。

## 設計の考え方

このテンプレートが前提にしていることを書いておきます。合わないなら変えてください。

**計画は「何を変えるか」より「何を見落としているか」で決まる。**
だから Refute と Gaps に半分近いエージェントを割いています。
草案を作るのは1体ですが、それを崩しにいくのが4体です。

**エージェントに決めさせない。**
仕様が曖昧なとき、もっともらしい計画を出すのは簡単です。
しかしそれは「人が決めるべきだったこと」を隠します。
だから `open_decisions` を第一級の出力にし、推奨は述べても決定はしません。

**記憶はファイルに置く。**
会話は消えます。`project-rules.md` と `backlog.md` だけが次のセッションに引き継がれます。
だからワークフローは毎回この2つを読むところから始まります。

**手動の検証を軽視しない。**
テスト基盤が無いプロジェクトは珍しくありません。
`regression-checklist.md` はその現実に対する答えで、
自動テストができた後も「画面が動くか」の確認手段として残ります。
