# 指摘・症状を直す手順

CLAUDE.md から呼ばれる手順書。**次のどれかに当たったら、直す前に必ずこのファイルを上から読む。**

- レビュー（review-full・code-review など）の結果が貼られたとき
- CLAUDE.md「### 6.」の (1) のテスト・(3) の突き合わせ・(5) の E2E、またはこのファイルの手順7で、
  想定外の失敗・食い違い（症状）が出たとき
- 赤になるはずのテストが赤にならなかったとき（CLAUDE.md「### 5.」）
- 回帰チェックリストの確認で壊れていたとき
- 計画書の step に無い実装・修正（頼まれた修正・変更・機能の追加、見つけたバグ）を始めるとき
- ユーザーがレビューの往復（ループ）を終えると決めたとき（手順9）

**どれも、原因を確定させてから、その分の計画書を作って直す。推測で直さない。**
誤りの無い変更の依頼は、原因の確定を飛ばして計画書から始める（手順2）。**計画書の承認より前に、テストも実装も書かない。**

## 流れ

```
入口: レビューの指摘 → 1. 仕分け（実在しないものは、入口ごとの行き先へ）
      症状・頼まれた修正・見つけたバグ
  ↓
2. 再現を試す（scratchpad）
  ├ 1回目で指摘どおりに赤、誤りの行を file:line で言える → 原因が確定
  └ それ以外 → /diagnose（Phase 5 に入らない）→ 原因と最小の再現を持って 3. へ
  ↓
3. 試作して反例を探す（共有の規則・関数を変えるとき）→ 計画書を作る（1章に原因、5章に約束と確かめ方）
  ↓
4. 承認 → 計画書だけコミット → 固定点を控える
  ↓
5. 再現テスト（赤）と守りのテスト（固定点で緑・壊すと赤）を書く
  ↓
6. 直す（再現テストが緑）
  ↓
7. 固定点と HEAD の出力を突き合わせる（意図しない差は症状として 2. へ）
  ↓
8. CLAUDE.md「### 6.」へ戻る → 入口が review-full なら review-full、push 前の code-review なら code-review を回し直す
  ↓（ユーザーがループを終えると決めたら）
9. 終わりのレビュー（ループの起点の要件・約束と、変えた決定の一覧で、変更の全体を1回見る）
```

review-full の指摘を直して、また review-full にかける往復を、このファイルでは**ループ**と呼ぶ。
ずれを防ぐのは2段で行う。**ループの各回**で起点の約束を引き継いで確かめ（手順3・手順7）、**ループの終わり**に
変更の全体を起点の約束と照らす（手順9）。各回の review-full は、その step の差分と切り出した仕様書しか見ないので、
修正を重ねるうちに起点の要件や約束からずれても、どの回のレビューにも映らない。

## 1. 仕分ける

指摘を1件ずつコードと照らして、**実在 / 誤検知 / 既存のブランチに元々ある問題 / 相談が要る** に分ける。
実在するものは1件ずつ手順2へ。実在しないものの行き先は、入口で変わる。

| 入口 | 誤検知・既存のブランチに元々ある問題・相談が要るもの |
|---|---|
| review-full | 理由を添えて報告し、止まる（直すかどうかはユーザーが決める） |
| push 前の code-review（CLAUDE.md「### 7.」） | 直さずに残し、push 後に PR のコメントで理由を添えて伝える |

**既存のブランチに元々ある問題は直さない**（この修正が持ち込んだものだけを直す）。

### 終わりの基準（実在する指摘を、直すか受け入れるかに分ける）

review-full・code-review は壊れる入力を探す向きのレビューなので、直すたびに何かは見つかり続ける。
基準が無いと往復が終わらない。実在する指摘は次の表で分け、**分けた案をユーザーに示して決めてもらう**。

| 分け方 | 当たるもの | 行き先 |
|---|---|---|
| 直す | 正しい入力・現実の使い方での後退（前の版で正しかったものが壊れた）、計画書5章の約束の違反、仕様の取り違え、テストの抜けと弱さ | 手順2へ |
| 直す（不正な入力でも） | セキュリティ、処理時間（悪意のある入力で止まる・入力の2乗で遅くなる）、データの破損 | 手順2へ |
| 受け入れる | 仕様や規格の上で正しくない入力（閉じ方の壊れた HTML、型の合わない JSON、ありえない状態の組み合わせなど）でだけ起きるもの | 計画書9章に足す（承認後の追記であることを、step のコミットメッセージに書く） |

- **受け入れるものを守るテストは足さない。** 欠落をそのまま固定すると、あとで直すときにテストが邪魔をする
- **同じ系統の指摘が2回続けて出たら、直し方そのものを見直す。** 規則を足して塞ぎ続けると、塞いだ所の隣で
  また漏れる。仕組みを変える（参照実装に寄せる・処理の段を変える）か、受け入れるかをユーザーと決める
- 計画書の1章か9章に、その回に使った基準を書いておく（次の review-full の仕分けで同じ基準を使うため）
- **ループを終えるかどうかはユーザーが決める。** Claude は仕分けの案を出すだけで、「ここで終わり」とは決めない。
  終えると決まったら、手順9の終わりのレビューへ進む

## 2. 原因を確定させる

計画書の1章（何を直すか・原因）と4章（変更ファイル）は、原因が分かっている前提で書く章。
原因が曖昧なまま書くと、4章が推測で埋まり、承認もその推測に対して出る。
だから計画書を書く前に、原因が確定しているかを**観察で**判定する。

**誤りの無い変更の依頼**（仕様の変更・機能の追加を頼まれた修正）は、再現する誤りが無いので、この手順を飛ばして手順3へ進む。

| | |
|---|---|
| 再現を試す | 指摘・症状に書かれた入力で、**指摘どおりの誤り**が出るかを確かめる。症状も同じく、まず再現を試す。置き場は scratchpad（計画書の承認前なので、リポジトリのテストにしない）。承認後に6章のテストとして書き直す |
| 原因が確定 | 再現が**1回目で指摘どおりに**赤になり、誤りを出す行を `file:line` で言えること。赤にならない・別の誤りで赤になる・行を言えない、はどれも「曖昧」 |
| 曖昧なとき | `/diagnose` に回す（バグの診断ループのスキル。このテンプレートには含まれない。SETUP.md「前提のスキル」。無い環境では、同じく「赤になる再現 → 仮説 → 計装」で原因を突き止める手段に置き換える）。`disable-model-invocation: true` なので Claude は起動できない。指摘か症状と、試した再現を引数に埋めたコマンドを提示して止まる |
| diagnose の止めどころ | Phase 1〜4（ループ作り・再現と最小化・仮説・計装）で原因を突き止めたら止める。**Phase 5（修正とテスト）に入らない。** 原因と最小の再現を持って手順3へ。Phase 5 に進むと、計画書の承認・守りのテスト・出力の突き合わせを通らずに直してしまう |
| diagnose のループ | 外へ書き込まない経路に限る（純粋な関数・読み取り系 API・外部をモックしたテスト）。DB・ストレージ・検索インデックスなどに書き込む API は叩かない。書き込みが絡む症状は、ユーザーが実行する手順を出す（diagnose の `hitl-loop`）。本番に計装を入れない |
| 後片付け | 手順3に進む前に、コードに入れた `[DEBUG-…]` のログを消す。使い捨てのハーネスは最初から scratchpad に置き、リポジトリに入れない。PR に載せる前に `git grep -n "DEBUG-"` で残りが無いことを確かめる |

## 3. 試作して反例を探し、計画書を作る

**多くの入力や呼び出し元に効く規則・共通の関数を変えるときは、計画書を書く前に、直し方を scratchpad で試作して
反例を探す**（CLAUDE.md「### 4.」）。壊す入力を探す向きのサブエージェントを1本走らせ、試作・固定点と過去の版・
正解の基準（仕様・参照実装・前の版の出力）・守りたい約束を渡す。見つかった反例と、試作での実測は、計画書の
1章・5章・9章に書く。直す範囲が1か所に閉じている（呼び出し元が1つ・入力の種類が限られる）ときは飛ばしてよい。

| | |
|---|---|
| 置き場 | `docs/plan/<機能キー>-<YYYYMMDD>-<主題>.md`（例: `search-filter-20260401-review-fixes.md`） |
| 章立て | 元の計画書と同じ番号を使う。当てはまらない章は「該当なし」と書いて番号は残す |
| 1章 | 何を直すか・依頼の出どころ・原因。指摘の URL や依頼の原文と、手順2で確定した原因（`file:line`） |
| 4章 | 変更ファイル |
| 5章 | 影響範囲・既存バグ・後方互換。**変わってはいけない振る舞い**をここに挙げ、**1行ごとに確かめ方**（どの道具が・どの入力の集合で）を書く。入力の集合が約束を覆っているかを見る（約束に効く組み合わせ・位置・状態が入っているか）。手順5の守りのテストと手順7の突き合わせの元になる |
| 6章 | 書くテスト。直す内容の再現テスト（赤→緑）と、守りのテスト |
| 8章・9章 | 回帰項目・リスク |
| 10章 | step |

### ループの中で計画書を作るとき（2段の1段目）

**ループの起点**は、ループの最初の review-full にかけた step。**起点の計画書**は、その step 1つ分の仕様。

| ループの始まり方 | 起点の計画書 | 起点の固定点 |
|---|---|---|
| 機能の計画書（`docs/plan/<機能キー>.md`）の step N を review-full にかけた | step N を切り出した仕様書（計画書の全体ではない。後の step が「未実装」として読まれる） | step N に着手する直前のコミット |
| 計画書の step に無い修正（外部のレビュー指摘・頼まれた修正など）から始まった | その修正のために、このファイルの手順で最初に作った計画書（例: `search-filter-20260401-fixes.md`） | その計画書のコミット |

ループの2回目以降に作る計画書では、次の2つを前の計画書から引き継ぐ。

- **起点の約束を5章に引き継ぐ。** 起点の計画書の5章の「変わってはいけない振る舞い」を、確かめ方ごとそのまま載せる。
  起点の約束を変えるときは、下の決定の一覧に「変えた」と書き、承認を得る（黙って外さない）
- **決定の一覧を1章に引き継ぐ。** 前の計画書の一覧を写し、この回の決定を足し、変えた行の状態を直す。
  最新の計画書を1本読めば、ループの中の決定が全部分かるようにする

  | 決定 | 中身 | 出た計画書 | 今の状態 |
  |---|---|---|---|
  | D-n | 何をそう決めたか（1行） | `<計画書のファイル名>` | 有効 ／ 狭めた（D-m で）／ 取り消した（D-m で） |

引き継がないと、決定が何本もの計画書に散り、途中で取り消したものも混ざって、今どれが有効かを知るのに
全部を開くことになる。起点の約束を途中の step で破っても、次の回のレビューでたまたま見つかるのを待つしかない。

## 4. 承認を得て、計画書だけをコミットする

作った計画書をユーザーに示し、**承認を得てから**テストを書く。
承認後、step に着手する**前に**計画書だけをコミットし、そのあとで固定点（`git rev-parse HEAD`）を控える。
**作業中の step の変更がまだコミットされていなければ**（step の途中で症状が出たとき）、計画書より先にその変更を WIP としてコミットする。
そうしないと、手順5の「固定点で緑」と手順7の突き合わせに、作業中の step の変更が全部「差」として混ざる。
順序が逆だと、review-full の差分に計画書自体が入る。

## 5. 直す前にテストを書く

- **再現テスト** — 手順2の再現を6章のテストとして書き、**赤を確かめる。** 赤にならなければ、直さずに手順2へ戻す
- **守りのテスト** — 直す箇所の周りで変わってはいけない振る舞い（5章）を固定する。
  直す前も後も緑になるので、赤の代わりに次の2つを確かめる
  - 固定点（直す前）で緑になること
  - 守っている振る舞いを一時的に壊すと赤になること（壊しても緑のままなら、そのテストは何も守っていない）

## 6. 直す

再現テストが緑になることを確かめる。
直した結果、意図して振る舞いを変えた箇所があれば、それも5章に書き、テストで新しい振る舞いを固定する。
**テストの無い場所で振る舞いが変わっても、テストの流し直しでは見つからない。**

## 7. 固定点と HEAD の出力を突き合わせる

5章で予想していなかった場所の変化は、守りのテストでは拾えない。
直したあと、固定点と HEAD に同じ入力を通して出力を突き合わせる。
差が出たら、意図した変化か確かめる。**意図しない差は症状なので、手順2へ戻す**
（原因を確定させ、守りのテストを足してから直す）。

- 対象は、同じ入力で同じ出力になり、外へ書き込まないコード（変換・抽出・整形などの関数）に限る。
  DB・ストレージ・検索インデックスなどに書き込む経路には使わない（共有環境が変わる）
- 固定点のコードは、scratchpad に `git worktree add` するか、`git show <固定点>:<path>` で取り出す。
  作業ツリーを checkout し直さない。`git stash` も使わない（stash は他の worktree・セッションと共有）
- 突き合わせに使ったスクリプトは scratchpad に置き、リポジトリに入れない
- **ループの2回目以降は、直前の固定点に加えて、ループの起点の固定点とも突き合わせる**（手順3「ループの中で
  計画書を作るとき」）。起点の約束からのずれを、ループの終わりを待たずに毎回見る。決定の一覧で変えた振る舞いの差は、
  意図した変化として扱う

## 8. CLAUDE.md「### 6.」に戻る

この修正を1つの step として、CLAUDE.md「### 6.」の (1)〜(6) と (8) を進める。(7) の代わりに、入口ごとに下の戻り先へ進む。

| 入口 | 戻り先 |
|---|---|
| review-full | 「### 6.」(7) で、この修正を review-full に依頼して止まる |
| push 前の code-review | 「### 7.」で code-review を回し直す。実在する指摘が0件になったら push する |
| 赤にならなかった（計画どおりの step で） | 新しい計画書は作らない。手順2で確定した原因に合わせて、元の計画書のその step（4章・6章）を直してユーザーに示し、承認後に「### 5.」から続ける |
| 症状・頼まれた修正・見つけたバグ・回帰チェックリスト | 「### 6.」(7) で review-full を依頼して止まる |

review-full の結果を見たユーザーが、ループを終えると決めたら、手順9へ進む。

## 9. 終わりのレビュー（2段の2段目）

ユーザーがループを終えると決めたら、ループの変更の全体を、起点の要件・約束と照らして1回レビューする。
PR を作るなら、push の前に行う。

| | |
|---|---|
| 範囲 | `git diff <起点の固定点>...HEAD`（手順3「ループの中で計画書を作るとき」の表）。PR の差分と同じ範囲なら、CLAUDE.md「### 7.」の push 前の code-review と兼ねてよい |
| 仕様書 | 次の3つを抜き出して1つにまとめる: ① 起点の計画書の1章（要件）と5章（約束と確かめ方） ② 最新の計画書の決定の一覧 ③ 各計画書の9章で受け入れた制約。置き場は scratchpad。作る前に、抜き出す範囲を示して許可を得る（CLAUDE.md「### 6.」(7) と同じ） |
| 見るもの | 起点の要件が満たされているか。起点の約束が全体で守られているか（決定の一覧で変えたものを除く）。要件と約束のそれぞれに、テストか確かめ方があるか |
| 依頼 | `/review-full <起点の固定点> <仕様書>` を示して止まる |

- **起点の計画書だけを仕様書にしない。** 後の計画書で正当に変えた決定が「仕様違反」として出て、往復がまた始まる
- **結果のうち直すのは、要件の取りこぼし・起点の約束の違反（決定の一覧で変えていないもの）・テストの抜けだけ。**
  新しい入力の組み合わせの指摘は、手順1の終わりの基準で仕分ける。正しくない入力でだけ起きるものは9章に足して
  受け入れ、ループに戻さない。終わりのレビューを、次のループの入口にしない
- 直すものが出たら、その分を1つの step として手順2から進める。終わりのレビューをもう一度行うかは、ユーザーが決める
