## 検証の層

| 層 | 実行 | 書き込み | Claude の自動実行 |
|---|---|---|---|
| 契約テスト（あれば） | （コマンド） | なし | **常に。** 層をまたぐ契約を触ったら必ず |
| 単体テスト | （コマンド） | なし | **常に** |
| フロントのテスト | （コマンド） | 通信をモックするので**実際の書き込みは起きない** | **常に。書き込みのフローも自動実行してよい** |
| 結合テスト | （コマンド） | **読み取り系だけ**（できれば、書き込み系の API を叩いていないことを機械的に確かめるテストを置く） | 外部への接続があるとき |
| E2E | （コマンド） | 書き込みは実行時に遮断する（下の「(5) E2E」） | アプリを起動し、外部への接続があるとき。**1回ごとに費用がかかる** |
| 回帰チェックリスト | ブラウザ操作のスキル + 人 | 行ごとに違う | 行の印で分担する。自動で確かめてよい行は Claude が流し、データが変わる行は手順を出すだけ |
| 手動 | 人 | **実際にデータが変わる** | **禁止。手順を出すだけ** |

状態を変える API は、**共有環境を壊すのでテストから叩かないこと。**

## (1) 自動テストを走らせて、結果を貼る

（このプロジェクトのテストのコマンドを、リポジトリルートから流せる形で書く）

コマンドの中で `cd` するときは `( )` で囲む。シェルの `cd` は残るので、続けて別のテストを打つと
対象の無い場所で走り、**エラーではなく「0件」が出る**（0件を成功と誤読する）。

**この step の6章に挙がっているテストが緑になったか**を、テスト関数名で示すこと。
「全部通りました」では、そのテストが実際にこの step を守っているか分からない。

## (2) 手動が要るものは「手順」だけ出す。実行しない

共有環境や本番のデータを変える検証は**ユーザーが画面から実行する。** Claude は次を出す。

- どの画面のどのボタンを、どの順で押すか
- 何が起きれば合格か
- **実行前に控えておく値**（件数・ハッシュ・最終更新日時など）

**共有環境を壊す操作は、明示の許可があるまで実行しない。**

## (3) ユーザーが実行したら、Claude が突き合わせて報告する

**画面を見て「動いた」で済ませない。** 実体を読んで整合を確認する。
**消えたはずのものが本当に消えたか**、**残ったはずのものが残っているか**を、データの側から見ること。

| 見る場所 | 何を見るか |
|---|---|
| （このプロジェクトのデータの置き場） | （件数・対象行のフィールド・最終更新など） |

**孤児（管理用の一覧に無いのに、実体が残っているもの）を必ず見ること。**
画面に出ないのに検索などで使われ続けるので、人の目では見つからない。

読み取りだけの一時プローブを置いてよいが、**確認後に必ず消す。**

## (5) 自動化できるものを手動に流さない — E2E に回す

自動テストでカバーできず、かつ自動実行しても危険でないものは、
**手動ではなく E2E に回す。「候補として挙げる」で止めないこと。**
どの層で確かめるかは、次の表で決める。

| 確かめたいこと | 行き先 |
|---|---|
| リクエストの組み立て・画面の状態遷移 | **フロントのテスト**（通信をモックするので速く、外部も要らない。書き込みのフローも自動実行してよい） |
| API の入出力・スキーマ | **結合テスト**（**読み取り系だけ**） |
| フロント・バック・外部サービスが実際につながっているか | **E2E**（ストリーミングが最後まで流れる・原本が開く・通知が届く など） |
| 実際にデータが変わるもの | **手動**（E2E でも同じことが起きる。ツールの問題ではない） |

E2E を作るときは、次を入れておく。

- **開発サーバではなく、配信するビルド成果物を叩く。** 実行前に、配信中の成果物とリポジトリの成果物が一致するかを確かめ、
  食い違えば1本も走らせずに落とす。ビルドのし忘れと、別のディレクトリのサーバがポートを掴んでいる事故を、ここで止める
- **書き込みは実行時に遮断する**（テストランナーのリクエストの横取り機能で）。E2E ではどの API が飛ぶかをアプリのコードが決めるので、
  テストのソースを grep しても違反は見えない。許可する書き込み（ログの追記など）は、理由を添えて列挙する
- **spec は、遮断を組み込んだ `test` から import させ、契約テストで機械的に強制する。**
  ランナーの素の `test` を使うと、遮断が効かないまま共有環境を壊せる
- **E2E は1回ごとに費用がかかる**（LLM の呼び出し・ログの書き込みなど）。
  検索や生成を伴う確認は、新しい spec を作らず、既存の spec の末尾に足す
- **アプリは決まった起動スクリプトで起動する。** アプリが環境変数ファイルを自分で読まない構成だと、
  直に起動して落ちたのを「ネットワークが切れている」と読み違えやすい。
  スクリプトは環境変数を読んでから起動し、起動せずに環境変数の有無だけを確かめるモードも持たせる
- E2E のテストと設定ファイルは、顧客に渡す枝から外す
