# PROJECT RULES — 計画時に必ず守る前提

> **このファイルはテンプレートです。** 中身をこのプロジェクトの事実に置き換えてください。
> 各節の説明文（引用ブロック）は書き終わったら消して構いません。
>
> `plan-survey` と `plan-feature` の**全エージェントが最初にこれを読みます。**
> ここに書いた事実は再調査されず、前提として扱われます。
>
> **書くのは人間。エージェントは追記を促すだけで、勝手には書き足しません。**

## 出荷の制約

> 「守らないと本番に反映されない」「守らないと壊れる」ことを書く。
> `plan-feature` はここに列挙された項目を**1つずつ引用して該当判定します**（`deploy_impact.hazards`）。
> だから、ここが空だと出荷事故のチェックが働きません。
>
> 書き方の例:
>
> ```
> 1. **フロントを変えたらビルド成果物のコミットが必須**
>    本番のビルド環境が古く、リポジトリに成果物を入れる運用。
>    忘れると本番だけ挙動が変わらない。
> 2. **依存を足しても反映されない可能性がある**
>    セットアップは venv に入れるが、サービスはシステムの python で動いている。
> 3. **環境変数を足したら本番の .env を手で更新する必要がある**
> 4. CI は存在しない。デプロイは手作業。
> ```

## テストの現実

> **正直に書く。** ここが計画の `verification` の書き方を決めます。
> テストが無いなら「無い」と書く。あるなら配置・命名・実行方法を書く。
>
> 書き方の例:
>
> ```
> 5. **テストフレームワークもテストコードも存在しない。**
>    pytest.ini / conftest.py / jest.config いずれも無い。
>    「既存のテストに倣う」は選べない。検証は次のいずれかで設計すること:
>    - 手動 QA 手順（画面操作の具体的な列）
>    - 使い捨ての検証スクリプト
>    - テスト基盤の新規導入（それ自体を独立したタスクとして切り出す）
> 6. **import 時に外部サービスへ結線するため、そのままではテストが書けない。**
>    `core/clients.py:186` の `clients = Clients()` がモジュール末尾にある。
>    ただし外部依存の無いモジュールは今すぐテストできる（列挙する）。
> ```

## 契約と壊れやすい箇所

> 片方だけ変えると型エラーも出ずに壊れるもの。**現物の一覧を書く。**
>
> 書き方の例:
>
> ```
> 7. **SSE のイベント名がフロント／バックで文字列一致している**
>    現在 8 種類: `query_creating` `index_searching` ...
>    送出は `src/server/stream_handler.py`、受信は `src/client/api/stream.ts`。
>    **イベントを足す/変える変更は必ず両側同時。** 片側だけ変えても型エラーは出ない。
> 8. **検索インデックスは 8 フィールド固定**
>    フィールドを足す = 既存文書の全再インデックスが必要。
> ```

> 書き方の例:
>
> ```

>     履歴を使う提案をする場合は「顧客合意の変更が必要」と明記すること。
