## 実装のたびに守ること

### 1. コードの新しい事実は `project-rules.md` に追記する

会話は消えるが、このファイルは残る。**次のセッションのエージェントが読む唯一の記憶。**
書かないと、次の計画で同じ調査と同じ質問が繰り返される。

**書くのはユーザー本人。Claude は勝手に書き足さないこと。**
ただし Claude は次の場面で追記を促すこと:

- 計画にもとづく実装が一段落したとき
- コードを読んで、project-rules に無い地雷や制約を新たに見つけたとき
- project-rules の記述が現在のコードと食い違っていることに気づいたとき

促すときは「追記してください」だけで終わらせず、**追記する文面の案を提示する**こと。
ユーザーはそれを見て採否と加筆を判断する。

セッション開始時のフックが、project-rules の最終更新以降に変わったソースを知らせる。

### 2. 決まった仕様は `backlog.md` に反映する

「決まっていること」と「決まっていないこと」の境界がこのファイル。
書かないと、計画ワークフローが決着済みの論点をまた聞いてくる。

### 3.（任意）構造が大きく変わったら地図を更新する

ディレクトリ再編や大規模リファクタで構造そのものが変わったときだけ、
`/plan-survey  lenses: ['ui', 'contracts']` で `docs/plan/repo-baseline.md` の指定したレンズを差し替える。
project-rules への追記で足りることが多い。project-rules を更新しても `repo-baseline.md`・`feature-order.md` は変わらない
（この2つはエージェントが生成する別系統。使い方は `.claude/workflows/README.md`）。

### 4. 計画の step ごとに、4〜9章を横断で読んでから実装する

`docs/plan/<機能キー>.md` の10章に step が並ぶ。**各 step に着手する前に、
4章（変更ファイル）だけでなく 5〜9章の該当箇所を拾うこと。**

4章だけを見て実装すると、その step に効く 5章（影響範囲・反証・既存バグ）、
6章（書くべきテスト）、7章（デプロイ）、8章（回帰項目）、9章（リスク）を落とす。
**落としても実装は動いてしまうので、落としたことに気づけない。**

5章に後方互換（変わってはいけない振る舞い）が挙がっていれば、6章のテストに無いものは守りのテストとして足す（「### 5.」）。

**あわせて `docs/plan/<機能キー>-note.md` の該当箇所も読むこと。**
これは計画を生成した入力（決めた仕様・設計判断 D-n・open decisions の回答）で、
**計画書に要約として落ちる過程で根拠や「なぜその案を捨てたか」が削られている。**
計画書の step 表が `D-8` や `Q-17` を参照していたら、**note 側の本文を必ず開く。**

**5章の「変わってはいけない振る舞い」は、1行ごとに「確かめ方」があるかを見る。** 確かめ方とは、
どの道具（テスト・出力の突き合わせ・手動の手順）が、どの入力の集合で確かめるか。とくに、**入力の集合が
約束を覆っているか**を見る（約束が「A の外は変えない」なら、A を含む入力の中の A の外も入っているか。
約束に効く要素の組み合わせ・位置・状態が入っているか）。確かめ方の無い行は、6章（テスト）か10章（突き合わせ）に
足してから着手する。約束が書いてあっても、確かめる道具がその入力を見ていなければ、後退はレビューまで見つからない。

**入力を変換する関数（抽出・正規化・整形・パーサ）の約束は、3つの向きで書く。** 「落とさない」
「余計なものを足さない」「区切り（段落・見出し・表・行）を変えない」。**入力の集合には、直しているバグの形とは別に、
正しく書かれた普通の入力を必ず入れる**（正しい入力を作る生成器か、実際のデータの保存）。
「落とさない」だけを測り、突き合わせの入力が壊れた入力の断片に偏っていると、何回レビューを通しても
「余計な文字が入る」「区切りが変わる」後退は見つからない。

**多くの入力や呼び出し元に効く規則・共通の関数を変える step は、実装の前に試作して反例を探す。**
次の種類の step では**必ず**走らせる: 入力の全体に効く変換（パーサ・抽出・正規化・整形）、認可の判定、
保存するデータの形（JSON・DB のキーや構造）。それ以外は、呼び出し元が1つで入力の種類が限られるなら飛ばしてよい。
scratchpad で試作し、**壊す入力を探す向き**のサブエージェントを1本走らせる。渡すもの: 試作、固定点と過去の版、
正解の基準（仕様・参照実装・前の版の出力）、5章の約束と確かめ方。見つかった反例は、計画書（5章・6章・9章）に
足してから本実装に入る。計画書と実装は「こう変わるはず」を確かめる向きなので、反例はレビューで初めて
見つかりやすく、そのたびに計画書から1往復かかる。

**計画書の step に無い実装・修正（レビュー指摘の修正、頼まれた修正・変更・機能の追加、見つけたバグなど）は、
テストを書く前に `fix-procedure.md` を開く。** 原因の確定 → その分の計画書 → 承認の順で進め、
以降はその計画書の step として「### 5.」「### 6.」を進める。誤りの無い変更の依頼（仕様の変更・機能の追加）は、
原因の確定を飛ばして計画書から始める（`fix-procedure.md` の手順2）。どれも、**計画書の承認より前にテストも実装も書かない。**

### 5. 計画の6章に書いたテストを、実装と同じ step で書く

**実装だけして6章を後回しにしないこと。** 後から書いたテストは新しい挙動を
写し取るだけで、**壊したかどうかを判定できない。**

**テストは実装の前に書いて赤を確かめ、実装して緑にする。**
先に赤を確かめられなかったテスト（既存のテストで守るときなど）は、直した箇所を一時的に戻して赤になることを確かめる。
**落ちない再現は再現ではない。** 「捕まえるはずのテストが素通りする」ことは実際に起きる
（再現のしかたが実物と違っていた、テストが定数しか見ていなかった、など）。
**赤にならなかったら、テストを書き換えて何度も試さず、`fix-procedure.md` に回す**
（再現のしかたか、原因の見立てが違っている）。

**守りのテスト**は、変わってはいけない振る舞いを固定するテスト。直す前も後も緑なので、
赤の代わりに次の2つを確かめる。

- 固定点（着手前）で緑になること
- 守っている振る舞いを一時的に壊すと赤になること（壊しても緑のままなら、そのテストは何も守っていない）

### 6. 各ステップの実装後にやること（この順序）

10章の step を1つ終えるたびに、**Claude が次を必ず実行して報告する。**
「一通り終わってからまとめて」は不可。**どの step で壊れたかが分からなくなる。**

**(1) のテスト・(3) の突き合わせ・(5) の E2E のどこかで、想定外の失敗・食い違い（症状）が出たら、その場でテストやコードを直さず、`fix-procedure.md` に回す。**
原因が確定する前に直すと、推測で直したことになる。

(1)〜(3) と (5) の手順の本体（層の表・手動確認・E2E の決まり）は **`verification.md`** にある。

| | やること |
|---|---|
| (1) 自動テスト | 自動で流してよい層のテストを流し、結果を貼る。**この step の6章のテストが緑になったかを、テスト関数名で示す** |
| (2) 手動の手順 | 共有環境や本番のデータを変える検証は**手順だけ出す。実行しない。** 押す順・合格の条件・実行前に控える値を出す |
| (3) 突き合わせ | ユーザーが実行したら、画面ではなく**データの側**を読んで整合を報告する。消えたはずのものが消え、残ったはずのものが残っているか |
| (4) 回帰項目 | 計画書8章（回帰チェックリストへの追記項目）のうち、この step で増えた行だけを、各行の印（種類・外部接続の要否）を付けたまま示す |
| (5) E2E | 単体テストでも結合テストでもカバーできず、自動実行しても危険でないものは E2E に回す。**「候補として挙げる」で止めない** |

#### (6) この step が「先へ送ったもの」が、送り先の step 行に書いてあるか確認する

step を終えるたびに、次の2つを必ず実行する。**書いていなければ、その場で計画書に追記する。**

- **① 先送りしたもの** — 「これは step N でやる」「次のリリースで」と判断したものを列挙し、
  `docs/plan/<機能キー>.md` の10章のその step 行を開いて、書いてあるか確かめる
- **② 変えた決定（D-n / Q-n）** — その決定を参照している step 行を grep して全部直す

**note に書くだけでは step 行を読む人に届かない。** step 行に無いものは、その step に着手する人の視野に入らない。
実際に、送り先の step 行に書かれていないものが3件まとめて見つかったことがある。
3件とも落としても実装は動き、テストも落ちず、計画書を読み直す以外に気づく手段が無かった。

#### (7) review-full を依頼して止まる

(1) と (5) のテストが全部緑になり、守りのテストの2つの確認（「### 5.」）と (6) の確認が済んだら、
Claude はこの step の変更を**ローカルでコミットし**（push はしない）、
次のコマンドを引数を埋めた形で示して**止まる。**
`review-full` は `disable-model-invocation: true` のスキルなので、起動するのはユーザー。
レビュー指摘を直した回も、1つの step として同じように扱う。

> `review-full` は、固定点以降の変更を規約・仕様・ロジックのバグ・セキュリティの観点で
> まとめてレビューするスキル（このテンプレートには含まれない。SETUP.md「前提のスキル」）。
> 無い環境では、手元のレビューの手段に置き換えてこの手順を使う。

```
/review-full <固定点> <仕様書>
```

| 引数 | 埋め方 |
|---|---|
| 固定点 | この step に着手する直前のコミット。**着手時に `git rev-parse HEAD` で控えておく** |
| 仕様書 | 下の表で用意したもの |

| この step が | 渡すもの |
|---|---|
| 計画の1つの step | **切り出した仕様書**（下記）のパス |
| 計画のすべての step にまたがる | 計画書 `docs/plan/<機能キー>.md` そのもの |

計画書の step に無い修正も、`fix-procedure.md` で先に計画書を作るので、このどちらかに当てはまる。

切り出した仕様書は、計画書から次の範囲を抜き出して1つにまとめたもの。
仕様と照らすレビューは渡された文書の全体を「この差分の要件」として読むので、
計画書を丸ごと渡すと、まだ手を付けていない後の step が「未実装」として指摘される。

- 10章の、対象の step の行
- 4・5・6・8・9章のうち、その step に該当する範囲（「### 4.」で着手前に拾う範囲と同じ）

**作る前に、抜き出す範囲（章と見出し）を示してユーザーの許可を得る。**
置き場所はリポジトリの外（セッションの scratchpad）。リポジトリに置くと step のコミットに
混ざり、レビューの差分にその文書自体が入る。

コミットしてから依頼するのは、`review-full` が `git diff <固定点>...HEAD` しか見ないため。
未コミットの変更はレビューされない。

**ユーザーが結果を貼ったら、`fix-procedure.md` を開き、その手順で仕分けて直す。**

**レビューの往復には終わりの基準を使う**（`fix-procedure.md` の手順1）。review-full は壊れる入力を探す向きの
レビューなので、直すたびに何かは見つかり続ける。実在する指摘は次の2つに分け、ユーザーに決めてもらう。

- **直す:** 正しい入力・現実の使い方での後退（前の版で正しかったものが壊れた）、計画書5章の約束の違反、
  仕様の取り違え、テストの抜けと弱さ。不正な入力でも、セキュリティ・処理時間（悪意のある入力で止まる）・
  データの破損に関わるものは直す
- **計画書9章に足して受け入れる:** 仕様や規格の上で正しくない入力（閉じ方の壊れた HTML、型の合わない JSON、
  ありえない状態の組み合わせなど）でだけ起きるもの

**同じ系統の指摘が2回続けて出たら、直し方そのものを見直す**（規則を足して塞ぎ続けない）。
基準が無いと、レビューと修正の往復が終わらない。

**往復（ループ）を終えるかどうかはユーザーが決める。** 終えると決めたら、`fix-procedure.md` の手順9の
**終わりのレビュー**へ進む（ループの起点の要件・約束と、変えた決定の一覧で、変更の全体を1回見る）。
各回のレビューは step の差分しか見ないので、修正を重ねるうちに起点の約束からずれても映らない。
ループの2回目以降の計画書の書き方（起点の約束と決定の一覧の引き継ぎ）は、`fix-procedure.md` の手順3にある。

#### (8) project-rules に追記する文面案を出す

この step で新しく分かった事実（`file:line`、実測値、**エラーが出ない壊れ方**）を、
`project-rules.md` に足す文面案として提示する。**書くのはユーザー本人。**

### 7. PR に push する前に、その PR の差分に code-review を回す

PR のブランチに push する直前に毎回（PR の新規作成・追加のコミットのどちらも）、
Claude が `code-review` スキルを effort `high` 以上で回す。

- **対象はその PR の差分だけ。** 固定点は PR の向け先で、範囲は `origin/<向け先>...HEAD`。
  回したあと、レビューされた範囲がこれと一致しているかを確かめる
- 引数にはレビューの範囲と「レビューの報告だけを返す。ファイルは書き換えない」を書く。
  修正モードのフラグ名は否定文の中でも書かない（含むだけで有効になる）
- 指摘は `fix-procedure.md` の手順で仕分けて直し、テストを流し直し、もう一度回す。
  **実在する指摘が0件になったら push する**
- 直さずに残した指摘は、push 後に PR のコメントで理由を添えて伝える
- **PR を作るとき、本文に「受け入れた制約」の節を設ける。** その PR に含まれる計画書の9章で受け入れたものを、
  「どんな入力で・何が起きるか・なぜ受け入れたか」で1行ずつ書く。理由は「ブラウザ（参照実装）も同じ」
  「仕様の上で正しくない入力でだけ起きる」「以前の版から変わらない」「別の直し方の副作用の方が大きい」の
  どれに当たるかを書く。コミットの SHA・レビューの回数・決定の番号は書かない（PR を見る人に通じない）。
  計画書は PR に載らないことが多いので、書かないと受け入れた理由が PR を見る人に届かない
- **PR の本文は、作ったあとは書き換えない。** レビューの指摘を受けたら、**コメントで返信する。** 直したものがあるときは、
  **先に push してから**、push したコミットを示して返信する（返信を読んだ人が、そのコミットで直したものを確かめられるように）。
  直すものが無いとき（全部受け入れた・誤検知だった）も、そのまま返信する。返信では、**レビュアーの指摘の1件ずつに**、直した（どう直したか）・受け入れた（入力・起きること・理由）・
  直さない（誤検知・相談。理由）のどれかを書く。あわせて、**直す中で新しく見つかって直したもの**（レビュアーの指摘に無い修正）を
  節を分けて1件ずつ、どんな入力で出力がどう変わるかを書き、新しく見つかって受け入れた制約と、影響も**全部**載せる。
  書かないと、レビュアーの知らない振る舞いの変更が、本文にもコメントにも説明の無いまま入る。
  本文を書き換えても通知は届かず、どこが増えたかも分からないので、コメントだけで何を直し、何を受け入れたかが分かるようにする

レビューの指摘を直すために足したコードを、レビューせずに push すると、直したつもりの箇所に新しいバグが残る。
大きな差分を対象にすると小さな競合は埋もれるので、PR の差分だけに絞って回す。

### 8. 機能を実装したら回帰チェックリストを一通り実行する

`docs/plan/regression-checklist.md` を上から順に確認し、壊れていたら直してから次へ進む
（直すときは `fix-procedure.md`）。
各機能の計画書の「回帰チェックリストへの追記項目」を、実装後にこのリストへ反映する。

## 計画ドキュメントはコミットする

`docs/plan/` 配下は上書きされるので、コミットしておくと
`git diff` で「どの決定が計画をどう変えたか」が読める。
`docs/plan/.baseline-commit` は地図の鮮度チェックに使うので消さないこと。
